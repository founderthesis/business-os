ACTIONS (decision 394). An action is one obligation of yours on an Engagement: a Zoya segment of Next action, or a substantive ask owed an answer on a thread linked to the row. Its key is "<engagement page id>:<type>:<origin>:<raised ISO timestamp with offset>". Origin: "msg-<Message-ID header>" (the inbound message that raised it), "call-<Activity or row id>" (Akshay's decision, his Your call, or the Activity that recorded it), or "seq-<routine>-<step n>" (a follow-up step); never derived from our own outgoing mail. Types and runs: reply, decision and hold are FAST's; followup (routines 1 to 6 and 8), nurture (routine 7, nurture, revival) and team (Jaya, Sarika, Ranjita, internal asks, payments, billing asks, vendor Your call steps) are SLOW's. A holding reply's key: type hold, the origin of the ask it acknowledges, raised when you send it. A Zoya segment carries its key in short form: "Zoya [<type> <origin> <raised ISO>]: <step>"; the engagement id is the row's.
- Old-format steps (no "[...]"): still yours by their wording and owner. Build the key at pickup from the row, the type the wording implies, the Activity or message that created it, and its Claude note date, and write it back onto that segment before acting. A follow-up STEP 2 selects by Status and Next date needs no wording: SLOW keys it itself as "<row>:<followup, nurture for routine 7>:seq-<routine number>-<step number>:<due date>T00:00:00+09:00" and writes that key onto the row as its segment the first time it selects it (send, hold or block), in place of the row's waiting segment for that ask ("Waiting on <their side>: ..."). Any other old-format segment still unkeyed is FAST's to key by the fixed keying rules on the developer page (Rules, Controls: "Zoya action keys"), never by free reading; one those rules can't type is reported and left alone. Snooze segments ("Zoya: back to Akshay on") keep their form. A Claude note date with no time keys as <date>T00:00:00+09:00. A seq origin's raised time is that step's due date (the date the previous step set, else the row's Next date when the step was written) at T00:00:00+09:00, never the day you pick it up.
- Reply owed means an unresolved substantive ask: a question, request or proposal from outside the team that no message from us has answered. Not owed: auto-replies, out-of-office, bounces, thanks or acknowledgements only, loop-ins, incidental Cc. An update with no ask gets only decision 404's bare emoji reply (Rules for Zoya), a FAST reply action, only on an update under 48 hours old, once per thread per 7 days (a payment or billing-details notice is SLOW's). An inbound that answers our open asks completes each, each completion line naming its Activity; two reply actions raised by one inbound key as msg-<id>-1, msg-<id>-2, in the order the asks appear; write each open reply action as its own segment "Zoya [reply msg-<id>-n <ts>]: <ask>"; an ask that goes to Akshay keeps that segment beside his "Ask Akshay" one, neither replacing the other. A holding reply or a loop-in answers nothing: the reply action stays open until the message that answers that ask, on the same thread.
- Before sending (before any hold rule): look for the action key on an Activity, then list the candidates: messages from us in your Sent to that recipient on the action's thread (a first mail with no thread: any thread) since the action was raised, whose Message-ID no Activity holds or only one with no Action key, less any that plainly does something else (another action's holding reply, a loop-in, another row's ask). The Message-ID on the action's Activity, or one candidate: that is the match: send nothing, log the Activity if it is missing, complete the action. None: it is due. Two or more: HOLD, never send: Akshay in Waiting on and one segment per candidate set, shared by the actions it holds, "Akshay: can't tell which mail completed <actions, short>: <each candidate's Message-ID and send time>. Write which in Your call", Claude note "YYYY-MM-DD: held for review (<keys>)", named in the report; a held action is skipped while that segment is open. Each run also checks its Sent for the last 24 hours, or back to the start of the latest run whose record isn't Completed if that is earlier: a message from us no Activity holds goes through this check for its thread's row (log the inbound it answers too); none it completes: log it there and report it; one named in an open "can't tell" segment: leave it. One message can complete several actions: one Activity, each action's completion line naming it.
- Send with the action key as idempotency_key on email_compose or the draft send (its SHA-256 hex if longer than 200 characters). Two Sent copies with one Message-ID are one send; a send found by the thread check gets its Action key too. Write "Action key" on the Activity only after a send receipt or a match above; an uncertain result leaves the action pending, retried with the same key after the thread check.
- WRITE PATH: every row write re-reads the row first and changes only this action's own segment of Next action (and the segments of asks the same inbound completes, each with its completion line), its own Waiting on entry and its own Claude note line; every other segment, owner and line stays as you found it, whoever wrote it. Then re-read: this action's segment, owner or note line missing, rewrite it once and report it. A write that changes Next action sets Next date to the earliest open segment date (a segment's date: the due date its text gives ("on", "by" or "original due", never a date the ask is about), else its key's; undated segments don't count, and with none dated it is the day of the write; "original due <YYYY-MM-DD>" counts; a snoozed or held-for-snooze one never does); any other write leaves Next date as it is.
